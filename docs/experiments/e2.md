# E2 — STT provider benchmark

**Code:** `app/e2.py` (latency / cost) + `notebooks/wer_ter.ipynb` (WER on the
golden set) · **Artifacts:** `docs/experiments/e2.json` · **Run:**
`uv run python -m app.e2 data/<course>`

## Goal

Quantify the quality / cost / privacy trade-off between the two STT providers
behind the `STTProvider` seam — local `whisper_cpp` (large-v3-turbo) vs cloud
`google_stt` (v1 `long_running_recognize`, `latest_long`, enhanced) — so the
choice per scenario is a table lookup, not a guess.

## Final table

| Provider | WER ↓ (golden) | RTF (latency) | $/audio-hour | Local |
|---|---|---|---|---|
| whisper.cpp `large-v3-turbo` | **2.3 %** | **0.123** | **≈ $0.04** (vast.ai) / **$0** own HW | yes |
| Google STT `latest_long` | 16.3 % | 0.141 | $1.44 (API) | no |

whisper.cpp wins every axis: 7× lower WER, comparable latency on a laptop, and
~30× cheaper even when its compute is priced at rented cloud-GPU rates. For the
9-lecture course (21.3 h of audio) the entire transcription cost ≈ **$0.92** at
vast.ai rates (or $0 on owned hardware) vs **$30.70** through the Google API.
Google's remaining advantages are purely operational: no local binary/model
setup and no machine tied up for ~8 min per audio-hour.

## Metrics

### WER — golden set (manual reference)

`notebooks/wer_ter.ipynb` scores each provider against the hand-corrected
reference in `data/golden-label/lecture-06/golden.md` (~19.5 min, 2:01:41 –
2:21:15, 2 090 reference words; standard normalization: lowercase, punctuation
stripped).

| provider | WER | sub | del | ins |
|---|---|---|---|---|
| whisper_cpp | **2.30 %** | 7 | 41 | 0 |
| google_stt | 16.27 % | 193 | 38 | 109 |

Google's errors are dominated by substitutions, and its misses include core
technical vocabulary of the lecture. Translation Edit Rate on the same segment
is within 0.1 pp of WER for both providers (few block moves), so it is not
reported separately.

### Latency

Recorded at transcription time by `app.transcribe` into
`<provider>/transcription.json` → `meta.latency_sec`; reported as **RTF**
(real-time factor = processing time / audio duration). Both providers were run
on the same machine and network (Apple M1, 16 GB; whisper.cpp Metal build,
`build-nocoreml`), over all 9 lectures of the course.

| provider | RTF (pooled, 21.3 h audio) | per-lecture range | 1 h of audio takes |
|---|---|---|---|
| whisper_cpp | 0.123 | 0.098 – 0.141 | ≈ 7.4 min |
| google_stt | 0.141 | 0.138 – 0.150 | ≈ 8.5 min |

Both are ~7–8× faster than real time and within 15 % of each other. Caveats:
google_stt's figure includes 16 kHz WAV extraction, GCS upload and
`long_running_recognize` polling (network-bound, machine-independent);
whisper_cpp's is pure local compute and scales with the hardware.

## Cost model

**google_stt — priced from the API rate card.** Speech-to-Text **V1**,
"Speech Recognition (without data logging)": `latest_long` is billed as a
*standard* model at **$0.024 / min** (after the free 60 min/month) →
**$1.44 per audio-hour** ([pricing page](https://cloud.google.com/speech-to-text/pricing),
retrieved 2026-07-16). GCS staging (the pipeline uploads a 16 kHz mono WAV
≈ 115 MB/h and deletes it after transcription) adds well under $0.01 and is
ignored. For reference, the V2 API would be $0.016/min ($0.96/h) with further
volume tiers, but the adapter uses V1.

**whisper_cpp — priced at rented-GPU rates from vast.ai.** Local inference has
no API price, so its compute is valued at what the same job would cost on a
rented GPU: `$/audio-hour = RTF × GPU $/hr`. RTX 4090 on vast.ai lists at
**≈ $0.34/hr** typical on-demand (range $0.29–0.59,
[vast.ai/pricing/gpu/RTX-4090](https://vast.ai/pricing/gpu/RTX-4090), retrieved
2026-07-16); with the default $0.35/hr and the measured RTF 0.123 →
**≈ $0.043 per audio-hour** (range $0.036–0.073). This is conservative: the RTF
was measured on an Apple M1 laptop, and a 4090 running whisper.cpp with CUDA is
several times faster than real-time-factor 0.123, so the true rented cost would
be lower still. On owned hardware the marginal cost is ≈ $0.

Both prices are marketplace/rate-card snapshots — rerun with `--google-usd-min`
/ `--gpu-usd-hr` to re-price without touching code.


## Known limitations / next steps

- **WER rests on one 19.5-min segment** of one lecture (lecture-06). The gap
  (2.3 % vs 16.3 %) is large enough to be conclusive for ranking, but the
  absolute numbers shouldn't be quoted with more precision than "~2 % vs ~16 %".
- **Latency was measured once per lecture** on one machine — RTFs are
  indicative, not a benchmark under controlled load.
- A label-free term-recognition metric (slide terms fuzzy-matched in the
  transcript) was prototyped and dropped from the write-up: the slide deck is
  too weak a reference (bibliography names and title-slide trivia are never
  spoken), so the absolute numbers weren't presentable. WER on the golden set
  is the quality metric of record.
- `[P2]` Term post-processing (a dictionary built from the slides fed back into
  decoding or correction) and measuring the WER gain is still open.
