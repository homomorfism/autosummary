**[00:53]** Over the last two weeks, we have discussed and built up a wide array of architectures and tools to solve various problems. Now we begin to apply them specifically to pictures. We already talked about pictures in the context of CNNs, but not yet in the context of Transformers. Alex already explained the Vision Transformer (ViT) in practice, so I won't spend much time on it. Our main plan for today is object detection.

**[01:56]** Object detection is one of the most interesting and hardest problems in computer vision, because its output structure is quite unusual compared to, say, segmentation. There is a lot to talk about, and Transformers come in very differently here. Usually, the Transformer just replaces some part of the architecture and serves as a better feature extractor, without conceptually changing the architecture. For example, in segmentation, the UNet architecture from 2015 is still used; modern versions simply replace convolutional layers with self-attention layers. The transformer did not make UNet obsolete. In object detection, it is a bit different.

**[03:48]** First, a few words on Transformers for pictures, Vision Transformers. I will not spend time on VisualBERT. VisualBERT was one of the first more or less successful approaches to handling pictures with Transformers. I will just describe the problem setting. It was mostly for captioning: you had text and object queries—tokens representing specific objects found in the picture. To use VisualBERT, you would first solve object detection to obtain these rectangles (subsets of the image corresponding to objects). Then you would pass them through a simple embedding layer to get a feature vector and then off you go with the Transformer. The point is that for the Transformer, it matters little whether the input came from text or images, as long as it is a sequence of vectors. The Transformer is great at finding internal correlations and structure among these vectors.

**[05:50]** It is no wonder that people eventually straightforwardly applied Transformers to images. Alex talked about this architecture, so I will not waste time, but the most striking feature of the ViT is its simplicity. There is absolutely no change in the Transformer architecture just because the input is an image. You might think that when you cut a picture into patches, they do not correspond to a natural one-dimensional sequence. For example, if you go row-first, adjacent patches in the sequence may not be close on the image. An image has a two-dimensional structure, so we might need changes in the positional encodings to tell the Transformer about the 2D structure. But it turns out, no. In the original ViT paper, they show that they tried several ideas for positional encodings and none of them help. You can simply treat it as a sequence and use standard positional encodings from text Transformers.

**[08:29]** ViT revolutionized computer vision and image processing because Transformers simply extract better, more semantically rich features. In many applications, you can just take out your convolutional network, plug in ViT, reuse the same top layers, and it will be better. Hundreds of papers did exactly this after 2020.

**[09:19]** However, there is one major problem: ViT and any Transformer have quadratic complexity, as we discussed. The attention weights form a token-by-token matrix of size $L \times L$, where $L$ is the input length. Thus, ViT’s complexity is quadratic in the number of patches. If you have height $h$, width $w$, and $k \times k$ patches, the number of patches is $(h/k)(w/k)$, and the attention matrix scales as the square of that number. This means you cannot have ViT go down to the level of individual pixels; a million pixels squared is too heavy. You must use relatively big patches, which makes it hard to capture small details. For instance, in object detection, if a small cat is entirely inside one patch or on the boundary, details get lost when flattening patches into vectors. There is really no correct patch size: too big loses detail, too small is computationally infeasible.

**[12:59]** There were many approaches to address this. I want to discuss one, the Swin Transformer, which is one of the most popular backbones today, alongside ViT. Swin stands for shifted windows. The idea is to break down the image into parts and then process each part with patches. Because complexity is quadratic in the number of patches, dividing into smaller windows significantly reduces computation. For example, a 2×2 grid of windows, each with a 3×3 patch grid, yields a local complexity of $9^2$, $6^2$, etc., summing to a few hundred, whereas the original 25×25 patch grid would be $25^2$, much larger. Thus, quadratic complexity becomes effectively linear in the total size, quadratic only in the window size. It is natural to have a hierarchical structure: first, cut the large image into small pieces (e.g., a 4×4 grid), process each part with a ViT, then combine them, process again with another set of ViT layers, and finally process globally with ViT layers.

**[15:31]** The SWIN transformer deals with 16 tokens at the input, only 4×4 grids. In three steps, we go from a 16×16 image to a 4×4 image, which is then compressed into features or a single vector. That is the basic idea. It is called shifted windows because of a problem that also appears in object detection: when you look inside small parts of the input image, you very often need more global context to understand what is happening. For example, you see a small part of some surface, and on it there is a vehicle. Because it is small, it is hard to distinguish exactly what it is. If you know the context is a highway with cars, then it is a car; if you know the context is a lagoon, then it is a boat. These are two very different classes, and without global context you cannot tell them apart. This happens all the time—global context is often necessary.

**[17:24]** So you would like these lower layers to obtain information about what is happening in the rest of the image. Shifted windows does this with a neat trick: between self-attention layers, you shift the windows. On one layer you have a regular grid of patches; on the next layer, the grid is shifted by half the patch size, but the transformer still sees the same input size—just a different subset of features from different parts of the image. If you do this after every layer, it expands the receptive field of the patches. A patch that originally only saw a small part of the image will, after two layers, collect information from a much larger area, because each shifted window aggregates features from adjacent patches. This is how the receptive field grows.

**[20:10]** There is, however, a messy implementation detail at the edges. When you shift the grid, the patches near the image borders are not full squares anymore. To handle this, they roll the image into a torus: the leftover edge pieces are paired with complementary pieces so that every window remains complete—rectangles go with rectangles, small corner squares go together as one window. This only affects the edges and ultimately does not matter much, but it is a lot of hassle. An implementation of a 3D SWIN transformer doing the same with cubes was the most convoluted code I have ever seen, full of hard-coded shifts and constants and very difficult to understand.

**[21:43]** In any case, the SWIN transformer and the ViT can both serve as good backbones. A backbone is the largest part of the network that does feature extraction. By default, the ViT is trained on something like classification: you extract features, collect them into a single vector at the end, and do global reasoning about the whole image. But today we are discussing a different kind of application that requires us to look inside the image and map our answers to specific pixels, which is always more difficult.

**[23:27]** Our main topic today is object detection. What is the problem? Informally, you have a large image that might contain, say, a cat, and perhaps other objects. Given the image and given a class (e.g., cat), you need to find the cat—not just say “there is a cat” with a confidence score as in classification, but also draw a rectangle around it, specifying exactly where in terms of rectangular coordinates (not down to individual pixels—that would be segmentation). This rectangle is called the bounding box, usually abbreviated BBox. The image may contain many objects of many classes, and for each object you must output the class label and a bounding box. Bounding boxes can overlap in any way.

**[26:46]** A bounding box is formalized by four numbers: typically x, y for one corner (say the bottom-left), then width and height. So the problem is: given an input image, a neural network must produce multiple outputs—one per object. For each object, you need a probability distribution over classes and the four bounding-box numbers. The tricky part is that a neural network cannot have a variable number of outputs. You must fix the total number of outputs. Per object you know exactly how many numbers you need (classes + four box coordinates), so if you knew how many objects are present, you would know the output size. But you do not know how many objects are in the image in advance.

**[29:59]** The number of objects in an image may be anything — a few cats and dogs, or hundreds — we never know in advance. So how can a neural network produce a variable number of outputs? A network must have a fixed number of output neurons with fixed, trainable weights, so the answer is simple: we fix a maximal number of objects we expect and provide that many output slots. This immediately raises another question: what if there are fewer objects? With, say, a maximum of ten slots but only a cat and a dog actually present, we need a way to mark the unused outputs as irrelevant. The usual fix is to add a confidence output — a probability between zero and one — that tells how sure we are that an object exists in a given slot. Each output then consists of a confidence, a class label, and a bounding box. With two real objects, we want those slots to have confidence one and all others confidence zero.

**[33:20]** Defining the output format is only the first step; we still need a loss function. We have an image and ground‑truth objects, each with a class and bounding box. How do we compare that to the network’s fixed‑size output? We cannot simply say that slot one should be the cat and slot two the dog, because objects have no natural order and the network should not be forced to sort them. We only want the real objects to appear somewhere with high confidence, and all other slots to have low confidence. This demands a matching between the ground‑truth set and the predicted slots — an assignment problem. By padding the ground truth with “no object” labels up to the fixed number of slots, we can find a bipartite matching that minimizes a cost. The Hungarian algorithm can compute this one‑to‑one matching, assigning each ground‑truth box to the best predictor.

**[36:46]** Matching alone is not enough; we must define the actual loss. Although details may vary, the loss usually has three components. First, a confidence loss: confidence should be one for real objects and zero otherwise — easily implemented as a log‑loss (e.g., $-\log(\text{confidence})$ or $-\log(1-\text{confidence})$). Second, a classification loss: applied only when an object is present, it is the cross‑entropy between the predicted class distribution and the ground‑truth class. Third, a bounding box loss: again applied only when an object is present, comparing the predicted box coordinates to the true rectangle.

**[38:41]** For the bounding box loss, you could use a straightforward L1 or L2 loss on the coordinates, such as $(x - x_{\text{pred}})^2 + (y - y_{\text{pred}})^2 + (w - w_{\text{pred}})^2 + (h - h_{\text{pred}})^2$. But coordinate‑based losses create a problem: they treat large and small objects very differently. For a large object, a moderate coordinate error still yields a lot of overlap and an acceptable prediction. For a very small object, the same coordinate error can produce zero overlap, making the prediction terrible even though the numerical loss value is similar. That is unintuitive; we want the loss to respect perceptual quality and penalize small‑object mistakes more.

**[40:56]** How to fix this? Some approaches, including the original YOLO, simply accept a coordinate loss. Nowadays a more common solution is to use a loss based on the Intersection over Union (IoU) metric. IoU between two boxes is the area of their intersection divided by the area of their union. For the large object, IoU might be 0.6–0.7 (a good match); for the non‑overlapping small object, IoU is exactly zero. IoU is the default metric for measuring box suitability. It is differentiable when the boxes overlap — small coordinate changes cause small IoU changes, giving meaningful gradients. However, when the boxes are disjoint, IoU stays zero and the gradient vanishes; moving the box slightly in any direction still gives IoU = 0, providing no learning signal. To solve this, Generalized IoU (GIoU) was introduced, providing a useful gradient even without overlap; the exact formula is beyond our scope.

**[43:53]** The loss function uses a common bounding box for two predictions and computes the percentage of the joint box not covered by both boxes. Moving predictions in the right direction shrinks the joint box and increases the overlap percentage, which is desirable.

**[44:45]** When applying the network, one more issue arises. So far I have only discussed loss functions, not architecture. This is intentional: architectures come and go, but loss functions are separate objects that only require gradients to flow through. They evolve independently, with dedicated lines of work optimizing losses and architectures separately.

**[46:51]** We have not quite finished with training. After finding the best assignment between ground-truth and predicted boxes, we must decide which predictions correspond to actual objects. For a predicted box overlapping a cat, we either want it to become the cat box with confidence 1, or treat it as a spurious box with confidence 0. In a typical image with only a few objects, most of the many output boxes should have low confidence. In practice, this is done with an IoU threshold (e.g., 0.5): predictions with overlap above the threshold are counted as ground-truth objects; those below are ignored.

**[50:29]** For clear, easy objects, a detection network with many output slots will often produce multiple bounding boxes around the same object. At inference time, when ground truth is unknown, we need to merge these hypotheses into a single box. The standard method is non-maximum suppression, which is used only at inference; during training we simply perform the best matching.

**[52:01]** To actually solve object detection, we need to consider network architectures. The first successful deep learning approach emerged in 2014 after AlexNet, called R-CNN (region-based CNN) by Ross Girshick. It used an external algorithm, selective search, to generate class-agnostic candidate bounding boxes. Each proposed box was warped into a square and passed through a CNN pre-trained on ImageNet to predict its class. This approach had limitations: the classification CNN always assumed the presence of an object and could not explicitly reject background, and the geometric warping was crude, but it was the best solution at the time.

**[56:09]** RCNN had a third step that took the CNN outputs and passed them through a separate model to classify whether each proposal was a real object. The approach was fragile but the best at the time, running at about a minute per image on a GPU. All the ideas of two-stage object detection are already in the original RCNN architecture.

**[57:22]** Although the field moved on, the RCNN family remains relevant for understanding the main ideas. The core idea is to use a backbone network to extract features from a specific part of the input. Candidate bounding boxes first come from an external algorithm (later, the network itself will produce them), providing a relatively small set of proposals. Each candidate is then processed through a CNN, its features extracted, and the content classified.

**[59:16]** Processing every bounding box completely independently is hopelessly slow. To achieve good coverage of objects, around 2,000 region proposals are needed, and the network, though fast per forward pass, must be run 2,000 times. This made the approach impractical.

**[59:59]** The next improvement, Fast R-CNN, processes the whole image only once. You run the image through a convolutional network but stop it a bit earlier than the final classification layer, preserving some spatial geometry in the resulting feature tensor. Candidate bounding boxes are then projected onto this feature tensor—a non-trainable region-of-interest (ROI) projection that maps each box to a corresponding spatial region in the feature map.

**[1:02:30]** From each projected ROI you run a small detection head containing a classifier for the object classes and a bounding box regressor. Even though proposals already exist, the regressor can refine the box (e.g., shifting it a few pixels), and it is trainable because we have ground truth. Since the heavy backbone is run only once and only the tiny detection head is applied per proposal, this is orders of magnitude faster than RCNN.

**[1:03:55]** A technical challenge is that different proposals have different sizes, and the detection head expects a fixed-size input. This is solved by ROI pooling. Given a feature map region of, say, \(3 \times 5\) and a required head input of \(2 \times 2\), you divide the region as evenly as possible into \(2 \times 2\) sub-windows and max-pool the features within each. This simple fixed-output-size pooling normalizes the input size and becomes a standard building block for object detectors.

**[1:06:35]** With Fast R-CNN, the remaining bottleneck was the external algorithm that generated the candidate boxes. The next iteration, Faster R-CNN, moves proposal generation inside the network via a region proposal network (RPN). The RPN works on the same feature map, sliding a small window across it and directly predicting which boxes are plausible. It outputs a few hundred top proposals, after which everything else remains the same: ROI pooling and the detection head classify and refine them. This is still a two-stage detector, but now proposals come from a learned component.

**[1:07:30]** Faster R-CNN became the standard approach to object detection for many years, until Transformers reshaped the field. Even in this architecture, you can plug in a better backbone (e.g., from VGG to ResNet to EfficientNet) without changing the rest of the pipeline, and you immediately get a better object detector. Two-stage detection, though accurate, is relatively slow, but it illustrates the key principles of the approach.

**[1:10:08]** From architectures to meta-architectures: a neural network extracts features and performs region proposals, while the top part – the heads – are basically fixed. The bottom part (the feature extractor) can be swapped out. Whenever a better feature extractor appears, object detection improves for free.

**[1:10:47]** I’ll speed up to reach transformer-based detection. A separate line of work is one-stage object detection, which processes the image in a single pass. In a two-stage detector, you first generate proposals, rank them, and then apply heavy processing only to the top proposals. In one-stage detection, you evaluate a set of candidate bounding boxes directly, but you cannot consider every possible rectangle (that would be quadratic in the number of pixels). Instead, you sample reasonable candidates at a fixed granularity. This is best exemplified by the YOLO family.

**[1:13:03]** The YOLO family uses a single neural architecture: it takes an image, evaluates many candidates in parallel, outputs results for all of them, and then you rank the outputs and keep the top predictions. The original YOLO was followed by YOLOv2, YOLO9000 (which handled many classes and introduced hierarchical softmax), and YOLOv3. These architectures improve through many small tweaks – each adding a few percent to accuracy – which collectively yield a large overall gain.

**[1:15:07]** The central problem of object detection, across both classical and deep methods, is detecting small objects. A large object (e.g., a cat covering a quarter of the image) is easily recognized by any architecture, such as the original Faster R‑CNN or YOLOv2. But a small object in the distance exposes a fundamental trade-off. In a CNN-based detector you stop at some intermediate feature map. If you stop too late, the grid is coarse; a small object may lie entirely inside one feature vector and its information is lost. If you stop too early, the grid is fine enough to see small objects, but then you must search over a huge number of candidate boxes, which is computationally infeasible.

**[1:17:57]** However, if you restrict fine-scale detection to only small objects, the quadratic complexity disappears. You can then do multi-stage object detection: pass the image through an early part of the CNN to obtain a fine grid (which is not yet semantically rich), run a region proposal network there for small objects, apply more layers to get a medium-scale feature map for medium objects, and further layers for a global-scale feature map for large objects. In this way, the three scales respectively detect large, medium, and small objects. This approach is more expensive but not prohibitive – with one catch: small objects still need global context to be recognized reliably.

**[1:20:33]** One of the most fruitful ideas after Faster R‑CNN was the Feature Pyramid Network (FPN). It takes a bottom-up CNN pathway to detect objects at multiple scales and adds top-down connections that fuse features from coarser scales into finer scales. Specifically, features from the coarsest scale are copied and fused with the medium-scale features, and those in turn are fused with the fine-scale features. This injects global context into the fine-scale detector, greatly improving small-object detection.

**[1:21:29]** FPN gave the network the ability to capture global context and became highly influential. Many subsequent works explored multi-scale, multi-stage object detection; the EfficientNet family used neural architecture search to find efficient backbones, and a parallel family searched for optimal post-processing, experimenting with bidirectional feature flow and skip connections—an inexpensive and flexible design space.

**[1:23:06]** Up to this point we have discussed what can be called classical deep-learning-based object detection. The appearance of ViT prompted the question whether transformers could simplify the task. The lesson of transformers in deep learning is that often a single excellent architecture can handle the problem if we just let it learn. Can a transformer sort out object detection? It turns out that it can, leading to a fascinating family of approaches.

**[1:24:52]** The first architecture in this direction is DETR (Detection Transformer). It still uses a CNN backbone to extract image features, adds positional encodings, and feeds the resulting sequence of vectors into a transformer encoder. The encoder merely processes these features; the detection happens in the decoder, which is a full encoder-decoder transformer. Instead of autoregressive generation, the decoder takes a fixed set of object queries—trained vectors (or sometimes fixed random ones)—and passes them through self-attention and cross-attention with the encoder outputs. Each output vector is then sent to a detection head that performs classification and bounding box regression. The number of detected objects equals the number of object queries, typically around 100, and most queries learn to output very low confidence. Queries specialize by location rather than class, and because they interact via self-attention in the decoder, they do not duplicate detections, completely removing the need for non-maximum suppression.

**[1:31:07]** A major limitation of DETR is its single-scale operation: the CNN backbone produces one feature map, and small objects lost during downsampling cannot be recovered. Visualizations show that decoder attention localizes on object boundaries and separates objects cleanly, but the single scale hampers small-object detection.

**[1:32:31]** Deformable DETR addresses this by running on multiple feature scales, like earlier multi-scale methods. More importantly, it introduces deformable attention. In DETR, attention already concentrates on object boundaries; deformable attention avoids the quadratic complexity of global attention by having each attention head look at a small, learned set of positions on the image. These positions are trained jointly with the rest of the network, allowing the transformer to process fine, multi-scale feature maps efficiently without prohibitive cost.

**[1:36:01]** We reduce our attention to a small subset of the input tokens. Then the next set of ideas is to work with the object queries themselves. They tend to specialize: on average, the boxes predicted by the object queries separate all over the input, which is great. But this learning happens very slowly, not really stable. Can we improve this? This separation doesn't look difficult to produce right from the start.

**[1:37:02]** Why not just take a grid or sample random points to help produce better object queries? Indeed, the next step uses this idea. Deformable DETR and dynamic anchor box DETR actually use anchors: the object queries are not just abstract vectors that learn over many epochs to predict different things, but are simply bounding boxes with meaning (X, Y, H, W). So you can initialize them smartly so they are separate from the beginning, and you have clear semantics between layers, allowing you to refine them in a smarter way. As a result, you get better object queries, better anchors, in less time. The best object detectors right now are DINO and its modifications, as well as Deformable DETR and others. All these architectures share the basic idea of the original DETR: the queries, representing objects/bounding boxes, are inputs to a transformer decoder, and the decoder fills them with content based on the image. There is a large body of research with many results and architectures.
